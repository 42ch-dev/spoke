# ADR: Adoption provenance as a dedicated protocol field with terminal-source resolution
Status: implemented — `KnowledgeEntry.adoption_anchor` wire, `AdoptionPort`, retirement-chain resolution, and the `knowledge.adopt` compound-gated connect op are in force
Date: 2026-11-23
Scope: `spoke-schemas` adoption wire, `spoke-operations` adoption helpers and `AdoptionPort`, `spoke-connect` dispatch and serving, `KnowledgeEntry.adoption_anchor`

## Problem

Adopting a shared `KnowledgeEntry` into a destination scope is a cross-host operation with no wire shape: provenance lives in product-private encodings (a `source_anchor.source_id` string prefix plus `extensions.mindcore_adoption` members) that a second host cannot parse without knowing the product convention. Every adopting host then disagrees on the anchor codec, on what a repeat call returns, on whether a moved (retired) source resolves or fails, and on whether a copy inherits the source's governance. Any two hosts implementing "adoption" diverge silently, and a copy's provenance pointer breaks as soon as the source moves.

## Proposal

Carry adoption provenance in a dedicated optional protocol field, `KnowledgeEntry.adoption_anchor`, with the closed shape `AdoptionAnchor { schema_version, source_scope_id, source_entry_id, source_revision, extensions }`. The field travels with the entry through get, put, and serve paths, and is immutable once written: a normal put preserves it byte-identically (RFC 8785 canonical equality) or refuses `ADOPTION_ANCHOR_IMMUTABLE` with `details.entry_id`. `source_anchor` keeps its own cross-product provenance meaning; adoption clears it on copies so the two provenance channels never mix.

Resolve retirement before writing: a `merged` source is resolved through its retirement chain to the terminal live source, following at most 32 edges after the requested entry and tracking every visited id. The anchor records the terminal source's scope id, entry id, and revision — never a retired intermediate — and the default destination id is the terminal entry id. A cycle, an ambiguous or unloadable chain node, a `deleted` terminal, or a required 33rd edge refuses `SOURCE_RETIRED` with `details.retirement_chain` (the ordered visited ids). Successor lookup stays storage-owned; the protocol owns only termination.

Reuse `REVISION_CONFLICT` for the different-revision repeat: an existing copy that anchors a different source revision refuses with `details.adopted_revision` naming the anchor's revision, and is never refreshed or overwritten. No adoption-specific revision code is added. Same-source same-revision repeats into the same destination return the existing copy as `already_present`.

Reset governance to the destination: the copy preserves `body`, `canonical_name`, `entry_type`, and `modules` minus `modules.cognition`; `owner` and `disclosure` take the destination's own values; `extensions` round-trips verbatim except the legacy `mindcore_adoption` namespace, which is dropped; `entry_id` is destination-assigned; the destination write is create-only OCC (`expectedBaseRevision: null`), with the source revision never serving as the destination's OCC base. The whole adoption is one atomic transaction, and idempotency is dual-layer: the entry-anchor repeat classifies an existing occupant, and connect-owned deduplication — keyed `(effective_scope, requester_principal_id, op, idempotency_key)` with a SHA-256 digest over RFC 8785 canonical JSON of the request — replays the recorded outcome instead of re-executing.

Expose the operation as one reserved-product connect op, `knowledge.adopt` under the new `knowledge.*` prefix, gated on `spoke-knowledge-adoption` with `spoke-knowledge` as a mandatory co-capability, served through a standalone `AdoptionPort` (`adopt_knowledge_entry(principal, scope, request)`) whose source and destination serving dependencies the host supplies, never the payload.

## Alternatives considered

- **Reuse `source_anchor` plus a product extension namespace for provenance.** This is the incumbent private codec. It needs no schema change, but a string-prefix convention is not a contract: a second host cannot discover or parse it, unknown extension namespaces are opaque by design, and adoption provenance would ride a field whose contract serves a different purpose (cross-product source citation). A first-class optional field makes the anchor readable and preservable by every conforming host.
- **Copy the requested entry as-is and let readers resolve retirement later.** This avoids resolver logic on the write path but defeats the anchor's purpose: the durable pointer would name a retired intermediate, every reader re-implements resolution per host, and stale pointers accumulate. Resolving once at adopt time and pinning the terminal source keeps reads cheap and the pointer stable.
- **Unbounded chain resolution.** Following a merge chain without a limit is simpler to state but allows non-termination on cyclic data and unbounded read cost on the write path. A 32-edge bound with the visited-id trail in `details.retirement_chain` makes refusal deterministic and diagnosable; chains deeper than 32 edges are re-requested against the terminal entry.
- **A new adoption-specific revision-conflict code.** A distinct code would grow the refusal vocabulary without adding meaning: `REVISION_CONFLICT` already says "stored base differs from expected", and `details.adopted_revision` carries the adoption-specific fact. Reuse keeps the vocabulary closed and client retry logic uniform.
- **Inherit source governance on the copy.** Copying `owner` and `disclosure` preserves the source's visibility policy in a scope the source's owner does not govern, which the destination host cannot apply or audit. Resetting both to the destination's own values keeps each scope's governance closed; the anchor alone records where the content came from.
- **Gate `knowledge.adopt` on `spoke-knowledge-adoption` alone, or reuse `spoke-knowledge`.** A single flag admits hosts that cannot serve the op: adoption needs the scoped serving infrastructure to admit source visibility and destination authorization. Reusing `spoke-knowledge` would make every scoped-serving host advertise an op it does not implement. The conjunctive pair keeps routing exact and fails closed (`capability_missing`) on partial declarations, following the family-core/sub-flag precedent of `spoke-memory`.
- **Entry-anchor repeat as the only idempotency layer.** Anchor classification alone cannot deduplicate a network retry that arrives before the copy is observable through any read path; the adoption would re-execute. Connect-owned deduplication with a recorded-outcome model (the `MemoryPort` pattern) closes the retry window before the admitted port call.

## Acceptance criteria

- `adoption-anchor`, `knowledge-adopt-request`, and `knowledge-adopt-response` schemas exist under `schemas/`, `KnowledgeEntry.adoption_anchor` is an optional `$ref` to the anchor schema, and `pnpm run verify-codegen` passes with both generated language packages and the schema inventory updated.
- Both language packages expose `AdoptionPort` with the principal-first, scope-at-port signature, the put-path anchor gate refusing `ADOPTION_ANCHOR_IMMUTABLE`, and the bounded retirement resolver (`RETIREMENT_CHAIN_MAX_EDGES = 32`).
- The connect dispatch gate admits `knowledge.adopt` only when `negotiated_capabilities` contains both `spoke-knowledge-adoption` and `spoke-knowledge`, answering `op_unsupported` / `capability_missing` before the handler with no side effects.
- The refusal vocabulary behaves as specified: `ADOPTION_ANCHOR_IMMUTABLE` + `entry_id`, `SOURCE_RETIRED` + `retirement_chain`, `REVISION_CONFLICT` + `adopted_revision`, generic `NOT_FOUND`, `IDEMPOTENCY_CONFLICT` with no adoption-specific details.
- Conformance vectors cover adoption, same-revision repeat, different-revision conflict, private-source absence, retirement-chain resolution, and anchor-immutability refusal across both languages.
- `.agents/specs/memory/spoke-knowledge-adoption.md` states the anchor shape, port semantics, copy rules, governance reset, refusal vocabulary, connect gate, and atomicity as affirmative facts, consistent with this record.

## Risks

- **The 32-edge bound refuses very deep merge chains.** A legitimate chain longer than 32 edges is refused rather than traversed; the `retirement_chain` details identify the terminal failure node so the caller can re-request against it. Borne by the caller, in exchange for deterministic termination.
- **Anchor immutability forbids refresh and re-anchoring.** A copy stays at its adopted revision; moving to a newer revision is a product-level operation (adopt anew under a new id or new key), not a protocol one. Borne deliberately to keep provenance trustworthy.
- **Dropping the `mindcore_adoption` extension namespace loses legacy product metadata on adopted copies.** The namespace's information is superseded by the anchor itself; products needing it on the destination must re-derive it from the anchor.
- **The conjunctive capability pair raises the declaration bar.** Hosts must declare two flags and misdeclaration fails closed at the gate rather than serving partially; the failure is diagnosable from the negotiation state.
- **Verbatim `extensions` copying can duplicate large product payloads into the destination scope.** The protocol round-trips unknown namespaces by contract and does not filter content beyond the legacy namespace; namespace size policy stays with the product.
- **Same-key serialization delays concurrent retries of one key.** The lookup → port → record section holds a per-key lock so a slow adoption delays only same-key replays, never cross-key adoptions; the recorded outcome makes the wait recoverable.
