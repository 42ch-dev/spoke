# ADR: C# binding generated through a vendored uniffi-bindgen-cs fork

Status: implemented — the C# binding ships from a vendored bindgen fork retargeted to the pinned uniffi 0.32 cdylib

Date: 2026-08-02

Scope: C# binding generation for the `spoke-connect` sync-core facade — bindgen version gap, the paths that were tried, the landed fork and its drop condition

## Problem

The product cdylib pins uniffi **0.32.0** and that pin is locked, because the same cdylib serves every uniffi language. The community C# generator `uniffi-bindgen-cs` at its latest published tag (`v0.11.0+v0.31.0`) targets uniffi-rs **0.31**, and no tag or main commit targets 0.32. The gap breaks the toolchain in two independent ways:

1. **`--library` metadata read.** The stock generator cannot read the exported `_UNIFFI_META_*` section of the 0.32 cdylib: `Error: extracting metadata for '_UNIFFI_META_SPOKE_CONNECT_CONSTRUCTOR_INBOUNDSEQUENCE_NEW' — Invalid string data (invalid utf-8 sequence of 1 bytes from index 1009)`. A positive control — the crate-local 0.32 `uniffi-bindgen` generating Swift from the same cdylib — proves the metadata is well-formed, so the failure is reader-specific.
2. **Runtime integrity gate.** The UDL fallback (a hand-written UDL mirror of the proc-macro surface) generates and compiles but every generated binding carries a checksum expectation the 0.32 cdylib cannot satisfy: all 14 exported symbols (8 functions, 3 constructors, 3 methods) mismatch, e.g. `check_response_correlation` expects 37894 while the library reports 57062. Those checksums derive from the uniffi metadata model, including the Rust module path, which a UDL cannot reproduce.

So the choice is between weakening the cdylib pin and owning a narrow generator patch.

## Decision

The C# binding is generated by a **vendored fork of `uniffi-bindgen-cs` retargeted to uniffi 0.32**, kept under `crates/spoke-connect/bindings/csharp/bindgen/` as patch, lockfile and build recipe. The fork is a 129-line source patch over 5 files: workspace uniffi dependencies 0.31.0 → 0.32.0, plus the uniffi 0.32 interface additions (`Type::Box` transparent, `Type::Set` handled by a new `SetTemplate.cs` HashSet converter). It restores the locked `--library` CLI form against the 0.32 cdylib.

The fork is **generation-only tooling**. The product cdylib keeps its single uniffi 0.32 pin, generated C# is committed and regenerated only when the FFI surface changes, and consumers never run bindgen. The landed result passes the contract-version and checksum integrity gates and reproduces the Rust golden vectors: the golden `peer_id`, hello signature, verify, and protocol version `1`, with the generated surface matching the FFI inventory exactly (8 functions + 3 objects + 2 error enums, rendering as 7 + 3 exception classes).

**Drop condition:** re-verify on any `uniffi-bindgen-cs` tag or main commit targeting uniffi-rs 0.32+, then replace the vendored build with stock `--library` and delete the fork. The regenerate → build → run sequence in the Smoke README is the re-check gate.

## Alternatives considered

**Stock primary pin (`uniffi-bindgen-cs <cdylib> --library`).** Failed on the metadata read — see the error above.

**Upstream `main` HEAD as a secondary stock attempt.** Failed identically: the latest tag and main HEAD are the same commit (`e10ce410eb3a10cc19c7928b93ea8d84e038c034`) and its workspace still pins 0.31.0.

**UDL mode (`uniffi-bindgen-cs <surface>.udl`).** Generation and a net8.0 csproj compile pass with no warnings, but the runtime fails the checksum gate on all 14 symbols, so the binding cannot load.

**Downgrading the cdylib's uniffi pin to 0.31.** Rejected: the pin is locked and shared with every other uniffi language served by the same cdylib, so a downgrade would trade one binding's convenience for the whole surface's version policy.

## Consequences

- One 0.32 cdylib continues to serve both C# and Swift; the Rust suite and Swift bindings are untouched by the fork.
- The fork is a maintenance obligation: an upstream release must be re-checked, and the patch re-applied or retired, whenever the bindgen line moves.
- Federation of toolchain versions is now explicit — bindgen version, uniffi pin and patch content are recorded together instead of being inferred from the CLI output.
- The C# outcome becomes the template for the feasibility gate every community generator must pass before its generated sources are committed, which is why Go reached the same vendored-fork conclusion and why the first-party generators (Swift, Kotlin, Python) need no such gate.
- Generated sources stay committed, so a reviewer can see the binding's shape in the diff rather than trusting a generator run.
