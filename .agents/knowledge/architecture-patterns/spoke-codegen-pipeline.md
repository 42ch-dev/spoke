# SPOKE codegen pipeline

**Category:** architecture-patterns

## Problem

Hand-authored JSON Schema must produce both TypeScript (`@42ch/spoke-schemas`) and Rust (`spoke-schemas`) without drift. Two generators (jstt + typify) have different `$ref` and naming constraints; a soft-failing Rust path can exit 0 with a partial tree; and typify's default field shapes lose wire distinctions the schema actually makes (present `[]` versus absent, any-JSON versus object-shaped JSON).

## Decision

1. **SSOT** — only `schemas/**/*.schema.json` are hand-authored; generated trees are committed.
2. **Orchestrator** — `tooling/codegen` (`pnpm -F @42ch/spoke-codegen codegen` → `node tooling/codegen/src/run.mjs`) walks schemas, localizes `$ref`s for typify, and emits mirrored `generated/{common,connect,data,ops}/` trees in both packages.
3. **Verify** — `pnpm run verify-codegen` runs `codegen` → `tooling/codegen/assert-schema-count.mjs` → `tooling/codegen/assert-opaque-json-types.mjs` → `node --test tooling/codegen/test/deep-ref-hoist.test.mjs` → `tooling/codegen/assert-generated-rust-size.mjs` → `git diff --exit-code` on both generated trees → `cargo check --workspace`.
4. **Fail-fast counts** — `assert-schema-count.mjs` holds `EXPECTED_SCHEMA_COUNT = 114`; `tooling/codegen/rust-gen/src/main.rs` holds the same constant and returns non-zero unless exactly 114 Rust schema modules are written. Bump both constants in the same commit as the schema change and the regenerated output.
5. **Closed ops responses** — mutually exclusive success/error shapes use draft-07 `oneOf` (see `assemble-response.schema.json`).
6. **Opaque JSON** — `#/definitions/OpaqueJson` must be an **empty schema object `{}`**. Consuming properties `$ref` that definition (e.g. `ComputableLogChange.previous` / `.next`, `ExtractionRunMetadata.coverage_hint`). Generators emit any-JSON types (`unknown` / `OpaqueJson` in TS; `serde_json::Value` in Rust).
6b. **Annotated `$ref` normalization** — a bare `$ref` to the untyped `{}` target emits `unknown`, but a `$ref` carrying a sibling `description` makes jstt emit an object-index map (`{ [k: string]: unknown | undefined }`), silently narrowing any-JSON to object shape. The orchestrator normalizes annotation-bearing opaque refs to the `allOf` form before generation, and `assert-opaque-json-types.mjs` checks the generated types with a negative control that names the regressed field. Connect `payload` / `auth` / `proof` are the precedent; adapting such consumers is a type-level mechanical change (object-map → `unknown`), not a wire change.
7. **Duplicate generated types (strategy A)** — document typify nominal duplication as known generator behavior; integrators use canonical `common/` imports. No orchestrator dedupe.
8. **Generated Rust size bound** — `assert-generated-rust-size.mjs` caps the three rustfmt-formatted memory response files (`memory_exports_get_response.rs`, `memory_imports_stage_request.rs`, `memory_receipts_get_response.rs`) at 2 MiB to catch runaway shared-definition growth. Raise the bound only with the legitimate schema change and the regenerated file in the same commit.
9. **Release tooling tests** — `pnpm run test:release` runs pure unit tests for lockstep assert/bump scripts (temp fixtures; optional `SPOKE_REPO_ROOT` for harness isolation). Wired into the CI `typescript` job.

## Schema inventory and generated layout

- **114** hand-authored `schemas/**/*.schema.json` files.
- Each generated tree contains **119** files: 114 per-schema modules plus 5 barrels (TS root `index.ts` and `common|connect|data|ops/index.ts`; Rust root `generated/mod.rs` and `common|connect|data|ops/mod.rs`).
- Counts are inventory, not proof: 119 files does not mean 119 schemas, a byte-identical regeneration proves generated bytes only, and neither says anything about downstream compilability (see *Regeneration ripple*).

## Presence-sensitive optional arrays

Typify maps an optional array to `Vec<T>` plus `skip_serializing_if = "Vec::is_empty"`, so an explicitly present `[]` serializes as absent. That is the canonical form for value objects, but it is wrong where sealed bytes are compared or counted. Two narrow rules exist in `tooling/codegen/rust-gen/src/main.rs`; neither generalizes to "all optional arrays".

1. **Module-wide (six byte-bound schemas)** — `PRESENCE_SENSITIVE_SCHEMAS` lists `data/memory-export-chunk`, `ops/memory-capture-request`, `ops/memory-exports-get-response`, `ops/memory-imports-stage-request`, `ops/memory-records-create-request`, `ops/memory-records-update-request`. In those modules *every* optional array becomes `Option<Vec<T>>` decoded through `deserialize_presence_sensitive_array`, so absent, `[]` and non-empty stay distinct while an explicit `null` stays invalid. Builders keep `Vec`-taking setters and wrap `Some`.
2. **Field-wide (`Content.cognition` only)** — `normalize_content_cognition_arrays` rewrites the `cognition` field of every inlined `Content` clone (typify names the owner `Content` or `SharedNN`), covering 15 carrier modules and 17 clone types. Unrelated optional arrays in the same struct keep the `Vec` + `is_empty` shape.

Why only there: chunk digests and Content byte accounting hash the sealed bytes, and `Content.cognition: []` (an explicit recorded empty set) is a different fact from "no cognition recorded". Everywhere else the canonical absent form governs — typify's skip makes `[]` serialize as absent, matching the schema rule that absent is never serialized as an empty array, and read paths normalize `[]` to absent outside the presence-sensitive carriers.

A schema-level `minItems` is not the tool for this: presence, not cardinality, carries the fact.

## Rust typify nominal duplication (strategy A)

typify dereferences `$ref` into each per-schema output module, so one `Content` definition is inlined into 15 carrier modules as 17 nominal clones, and a shared `common/` definition inlined into a `data/` or `ops/` module yields a second nominal struct with the same field layout (for example `SourceAnchor` inside `generated/data/timeline_event.rs` alongside the canonical `generated/data/source_anchor.rs`).

Facts for Rust integrators:

1. Duplicates are generator artifacts — they serialize the same JSON shape and are **not** separate wire types.
2. Import canonical shared types from `spoke_schemas::generated::common` or crate-root re-exports (for example `use spoke_schemas::Scope;` or `use spoke_schemas::ComputableLogChange;`). Do not use same-named structs from nested inlines inside other `generated::data::*` or `generated::ops::*` files.
3. Duplicate nominal structs are not interchangeable in Rust even when fields match. Convert via `serde_json` round-trip when bridging values; do not `as`-cast between them.

TypeScript (`jstt`) may emit parallel duplicate interfaces; import shared defs from `generated/common` the same way.

## Rust construction — exhaustive literals are source-breaking on new fields

`rust-gen` enables typify `with_struct_builder(true)`, so every generated struct exposes a `Builder` (e.g. `Scope::builder().scope_id(...).try_into()`). **Downstream Rust consumers SHOULD construct generated types via the Builder**, which stays source-compatible when SPOKE adds optional fields.

Raw struct literals (`Scope { scope_id: ..., ... }`) are **field-exhaustive by typify design**: every field — including optional ones like `entry_ids`, `entry_types`, `timeline_event_ids`, `fork_id`, `extensions` — is a concrete `Vec`/`HashMap`/`String` member (wire-optional only via `#[serde(default, skip_serializing_if = "...::is_empty")]`). **Adding any generated field is therefore a 0.x source-breaking change for downstream exhaustive literals** — call sites must add the field or migrate to the Builder. This is intentional and accepted as a 0.x breaking release (SPOKE is pre-1.0; wire JSON is unaffected — the field is optional on the wire, and TypeScript is unaffected).

**Migration for Rust consumers hit by a new optional field:** replace exhaustive literals with the typify Builder — `let scope: Scope = Scope::builder().scope_id(...).try_into()?;` (terminated via `TryFrom`/`try_into()`, **not** `.build()`), or add the field explicitly. It is **not** fixed by deriving `Default`: typify also generates enums (`BodyAttributeValue`, the `*Response` success|error `oneOf`s) with no `#[default]` variant, so a crate-wide `#[derive(Default)]` would not compile. Conventional Commits carrying a `BREAKING CHANGE:` footer flag these releases in the `CHANGELOG`.

## Regeneration ripple (generated ABI → downstream implementors)

Regenerating binding trees changes the **interface downstream host code must implement**, not only the generated files. A new callback method on `PortsHandler` makes every existing implementation of that interface (per-language smoke files, host staging) uncompilable until it implements the method:

- The ripple lands **outside** the generated trees, so a zero-drift, committed regeneration can leave channels unbuildable when their handlers were not updated in the same change.
- Per-task diff review cannot see this class: each diff looks correct in isolation, and the breakage appears only when the generated tree and its consumers compile together.
- Handle it deliberately: land the generated ABI and the downstream handler updates as **one task**, or make the regenerating task's acceptance include "the consuming smoke/host sources still compile". Zero-drift proof covers generated bytes; it says nothing about downstream compilability.

## What not to do

- Do not invent a custom codegen engine.
- Do not warn-and-skip failed schemas (CI would go green on partial output).
- Do not hand-edit generated files; regenerate.
- Do not `as`-cast between duplicate generated structs; convert via JSON round-trip if needed.
- Do not apply presence-sensitive array handling broadly: it exists for sealed byte carriers and `Content.cognition`, and widening it changes every typed round-trip.
- Do not treat a green count constant as coverage; add the vector or assertion that proves the new shape.
